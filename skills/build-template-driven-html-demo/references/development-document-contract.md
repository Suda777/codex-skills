# 开发文档内部契约

本文件规定如何把对话人确认过的开发文档，转换为可以直接驱动 HTML Demo 的内部契约。契约是生成阶段的唯一业务输入；模板只提供表现方式，不补写业务事实。

## 标准结构

先在内部整理为以下结构。没有内容的字段也要保留，并标明 `未提供`、`不需要` 或已采用的假设。

```yaml
meta:
  project_name: 匿名或演示名称
  demo_goal: 本次演示要让观看者理解或相信什么
  audience: 演示对象及其关注点
  scope_in: 本次必须演示的范围
  scope_out: 明确不实现的内容

pages:
  - id: overview
    name: 总览
    purpose: 页面解决的问题
    entry: 从哪里进入
    navigation: {visible: true, group: 工作台, order: 1}
    content: [模块、字段或指标]
    available_actions: [action_id]
    states: [默认态, 空态, 错误态或其他必要状态]

data:
  entities:
    - id: item
      meaning: 业务含义
      fields:
        - {name: status, meaning: 当前状态, type: enum, required: true}
      relations: [与其他实体的关系]
      representations:
        summary: [列表、卡片或搜索结果需要显示的字段]
        detail_sections: [打开后必须出现的完整业务内容区块]
        editable_fields: [允许在 Demo 中修改的内容]
        provenance: 来源实体、生成动作或手工录入
        downstream_consumers: [统计、报告、通知或其他使用该实体的视图]

actions:
  - id: update_status
    actor: 谁可以操作
    trigger: 在哪里点击什么
    preconditions: [操作前条件]
    input: [需要填写或选择的内容]
    effect: 数据、状态或页面如何变化
    affected_views: [需要同步刷新的页面、列表、详情、统计或下游结果]
    persistence: 仅当前会话 | 刷新后保留 | 不产生持久状态
    reversible: true | false
    destructive: true | false
    feedback: 成功、失败或校验提示
    destination: 留在原处、打开详情或跳转页面

journeys:
  - id: J-001
    goal: 使用者要完成的完整任务
    entry: 起始页面或入口
    steps: [按顺序引用 page_id 和 action_id]
    expected_end_state: 完成后用户能看到的数据、内容或状态
    affected_entities: [被创建、修改或汇总的实体]

rules:
  - id: R-001
    condition: 触发条件
    result: 必须发生的结果
    priority: must
    source: 开发文档原文或已确认结论

copy:
  page_titles: {}
  field_labels: {}
  button_labels: {}
  status_labels: {}
  empty_messages: {}
  validation_messages: {}
  success_messages: {}
  forbidden_terms: []

assets:
  - id: asset-01
    type: image | icon | logo | chart | map
    purpose: 使用位置与作用
    source: 用户提供路径、可复用来源或待生成
    rights: 可使用 | 仅参考 | 未确认
    fallback: 无资源时的安全替代方案

mock:
  entities: [需要构造的实体及数量]
  distributions: [状态、日期、地区等分布]
  relationships: [必须保持的数据关联]
  edge_cases: [需要出现的异常、空态或临界值]
  privacy: 全部使用匿名合成数据

assumptions:
  - id: A-001
    statement: 采用的假设
    reason: 为什么可以默认
    impact: low | medium | high
    reversible: true | false
    confirmation_required: true | false
```

## 提取规则

1. 将同一需求分别落到页面、数据、动作或规则中，不用一段自然语言同时代替多个字段。
2. 每个按钮、链接或可点击区域都必须对应一个 `action_id`；装饰元素不得伪装成可操作控件。
3. 每个全局或侧边导航项必须对应唯一的 `pages` 条目。只有真正需要从导航进入的页面才设为 `navigation.visible: true`；抽屉、弹窗和普通详情视图不得为了填满菜单而伪装成全局页面。
4. 每条关键规则必须能追溯到开发文档原文或对话人已确认的结论。发现冲突时保留冲突，不自行选择更顺耳的版本。
5. 页面字段必须来自 `data`；动作造成的变化必须反映到 mock 数据、状态或可见反馈中。
6. 开发文档没有指定普通布局或控件时，不把它记为业务缺口，由组件选择规则自动处理。
7. 文案优先使用开发文档中的称谓；缺少非关键说明文案时，可以按现有语气补写，并记录为低影响假设。
8. 图片、Logo、地图或字体未提供时，不联网临时抓取；使用内联 SVG、CSS 图形、匿名占位图或不展示。
9. 对可以被打开、查看、生成或保存的核心业务对象，同时定义摘要和详情。详情必须包含足以完成演示任务的对象特有内容，不能只重复标题、日期、状态等元数据，也不能让所有对象共用同一段泛化正文。
10. 对新增、生成、编辑、保存、删除、切换状态等动作，记录它影响的实体、视图和后续结果。若一个动作承诺改变数据，契约必须说明变化在何处可以再次看到；取消操作必须说明哪些状态保持不变。
11. 用 `journeys` 表达跨页面或跨组件的完整任务链。单个按钮都能点击不等于主任务已经闭环；至少要能从入口走到可观察的最终状态。
12. `destructive: true` 只用于真实删除、覆盖或不可逆行为。普通的筛选、停用、取消汇总、关闭和移出集合不得使用容易被理解为删除的名称或危险样式。

## 对话式需求整理

对话问题数量不固定，也不预设“必须十项”。AI 根据当前 Demo 的业务复杂度动态维护信息缺口，并始终一次只问当前最重要的一项。

优先闭合会影响 Demo 结构和逻辑的内容：演示目的与观看者、主要使用者、核心任务或流程、完整页面入口、点击后的结果、关键数据及关系、状态与计算规则、权限或办理边界、必须出现的文案或素材、明确只做模拟的能力。视觉细节和普通组件选择不进入必答队列。

对话人一次提供整段材料时，先完整提取再追问；分多轮讲述时，持续记录而不要求特定结束口令。对话人回答了其他内容时，将其归位到对应契约字段，然后回到尚未闭合的最高优先级缺口。不得因为聊天话题变化而遗漏原先必须确认的事项。

信息可能模糊时可以提出自己的候选理解，但要标明这是推断，并说明它会怎样影响页面或逻辑。高影响推断交给当前对话人确认；低影响、可逆的展示细节采用模板默认值并记录为假设。

## 什么时候必须追问

仅当缺口会改变以下任一结果时，才向当前对话人追问，而不是要求终端客户直接确认：

- 核心演示目标或主要使用者；
- 主流程能否走通、点击后究竟发生什么；
- 数据字段含义、实体关系或关键统计口径；
- 状态流转、计算、权限、审批、完成条件；
- 不可逆操作、合规风险或可能误导客户的事实；
- 两种合理解释会产生明显不同的 Demo。

追问时维护内部缺口队列，按影响从高到低一次只问一个问题。对话人回答了旁支信息时，先记录，再回到未解决的最高优先级缺口。颜色、圆角、按钮位置、普通图标、常规组件形式等不得作为追问理由。

无法取得关键答案时，不悄悄编造：把候选理解、影响和推荐默认值简短告诉对话人，由其确认后记入 `assumptions`。低影响且可逆的缺口可以采用默认值并记录，不阻塞生成。

## 生成前门槛

进入代码生成前，契约必须满足：

- 所有 `must` 页面、动作和规则都有唯一 ID；
- 每个可见导航项都已映射到一个完整页面，没有占位导航；
- 主流程中的动作具备触发点、结果和反馈；
- 每条主流程已形成 `journeys`，且终态可以在页面中观察；
- mock 数据足以触发正常态以及开发文档要求的异常态；
- 核心业务对象已分别定义摘要、完整详情、来源和下游使用关系；
- 高影响或不可逆假设已经由对话人确认；
- 开发文档中的每项必做需求都能映射到契约条目。

达到门槛后，先向对话人展示一份简短的“准备开发内容”：Demo 目标、页面、核心操作、数据关系和规则、Mock 范围、模板以及高影响假设。只有对话人明确认可这份摘要，才进入代码生成；认可后不再重新询问普通 UI 细节。
